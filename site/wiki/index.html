01

Getting started

Install deliberately.

ZenPi is review-first. Start with the non-mutating plan, confirm the install only when it matches your expectations, then ask the doctor to verify the result.

Requirements

Node.js 22.19 or newer, npm, and Git. ZenPi uses Pi 0.84.4 or newer and can install the reviewed pinned Pi release when Pi is missing.

1. Clone a reviewed release

terminalrelease v0.7.0
git clone --branch v0.7.0 --depth 1 https://github.com/TannerMidd/ZenPi.git
cd ZenPi

Windows

PowerShell / cmd
.\zenpi.cmd plan
.\zenpi.cmd install
.\zenpi.cmd doctor

Linux, macOS, or Git Bash

shell
./zenpi plan
./zenpi install
./zenpi doctor

What the lifecycle does

plan

Prints intended changes without mutating your system.

install

Confirms, backs up, writes atomically, and rolls configuration back if setup fails.

doctor

Checks managed files, settings, runtime dependencies, profiles, browser readiness, and every validator linked from the capability registry.

update

Refreshes managed resources while preserving unrelated settings and user-tunable state.

uninstall

Removes managed integration while retaining local evidence, profiles, and external packages.

02

First session

Begin with three small moves.

  1. 1
    Reload Pi

    After installation, run /reload so Pi loads ZenPi's extensions, skills, theme, and managed settings.

  2. 2
    Enter focused mode

    Run /zen to use ZenPi's quiet execution surface. Run it again when you want to leave.

  3. 3
    Choose local collection

    The wishlist asks once whether capability-gap collection should be on or off. Reports stay local and sanitized.

Nothing self-starts

Evidence can qualify a wishlist item, but only your explicit choice in /harness-improvement authorizes implementation.

03

Improvement loop

Let friction become evidence.

ZenPi is a control loop, not an autopilot. Repeated, reusable gaps rise into view; human judgment starts one bounded change; repository and capability gates decide when it is done.

01Friction

A real task hits a missing local capability.

02Repeat

Distinct tasks and projects establish reusable evidence.

03Choose

A person authorizes one exact wishlist item.

04Build

The smallest sufficient intervention is implemented.

05Prove

Repository checks and closed validators gate completion.

06Retire

Passing proof closes the item and journals evidence, gates, changed files, and version.

07Return

Later evidence links to that retirement and surfaces bounded context for human review.

Run an improvement

Pi commandone explicit choice
/harness-improvement

Choose a qualified or review-needed item. The zenpi-improve workflow scopes the intervention, makes the change, and gathers direct acceptance evidence. A failed gate leaves the item selected instead of pretending it is complete.

Inspect proof and loop health

/wishlist statusSummarize the queue, retirements, reopen rate, and open reviews.
/wishlist historyShow the latest retirement and reopen decisions across the local journal.
/wishlist history <gap-id>Show one gap's evidence, gates, changed files, linked reopens, and rollback context.

Every registry capability names a closed offline validator. Completion runs the source validator under review, while npm run check and zenpi doctor continuously re-prove shipped capabilities. Reopens include the original proof, a post-retirement signal window, and sanitized bounded Git context.

05

Delegation

Different model.
Same exact provider.

ZenPi can give built-in roles their own model and thinking level, but every explicit child model must remain inside the parent session's exact Pi provider.

/zen-subagentsConfigure the active provider's role profile and optional global capacity.
/zen-subagents statusInspect active roles, strict scope, saved providers, stale models, and capacity.
/zen-subagents resetReset only the active provider profile; other profiles and capacity stay unchanged.

Provider profile rules

  • Configure each exact provider once; ZenPi restores its profile automatically in later sessions.
  • openai, openai-codex, openrouter, and other provider IDs are separate boundaries.
  • inherit remains portable and follows the parent model.
  • Unavailable saved models become stale and are never silently replaced.
  • Role profiles are provider-specific; child budgets and active async capacity remain global.
  • Live processes on different providers fail closed rather than racing the shared settings mirror.
When Pi asks for a reload

If ZenPi restores a startup-loaded mapping, run /reload. Native launches stay blocked until the runtime and saved profile are aligned.

06

Command guard

Stop dangerous model commands before execution.

Interactive top-level sessions start with a choice: Guard blocks catastrophic operations and parser-integrity failures, and asks about other classified destructive or indeterminate work; Strict also asks about ordinary mutation and every uncatalogued tool; Off requires a second confirmation and lasts only for that session.

/guard statusShow mode, lock state, policy version, and in-memory counters.
/guard guardUse recommended critical-deny and high-risk approval behavior.
/guard strictRequire approval for a broader mutation and execution surface.
/guard offExplicitly disable protection for this top-level session.
/guard unlockReview and clear a lock created by a critical attempt.

The guard analyzes model calls to Bash and PowerShell, nested cmd syntax, protected reads/writes/edits, and supported direct native child launches verified through the pinned public pi-subagents/preflight contract. Print and JSON sessions default to Guard, and any decision needing a prompt is denied when no UI exists. Critical attempts lock later execution and child launches.

Defense-in-depth boundary

This is not an OS sandbox. Direct human shell escapes, malicious extensions, unclassified custom tools, approved or changing scripts, and external processes remain outside its hard boundary. Use least privilege, containers, or VMs for hostile code.

07

Browser QA

Inspect what users actually see.

ZenPi's browser tools open pages in a fresh isolated Chromium context. Use rendered snapshots and screenshots at relevant desktop, tablet, and mobile viewports; source inspection alone is not visual proof.

1Open

Load the local or remote page in isolated Chromium.

2Inspect

Read the rendered structure and exercise interactive controls.

3Resize

Validate desktop, tablet, and mobile layouts.

4Capture

Save bounded evidence or compare an explicitly approved baseline.

Isolation boundary

The browser never attaches to your personal Chrome profile, cookies, passwords, or extensions. It is process-isolated, not an operating-system sandbox.

09

Configuration

Know what ZenPi owns.

ZenPi merges documented leaves and preserves unrelated packages and configuration. Managed state lives under the Pi agent directory; setting PI_CODING_AGENT_DIR relocates the equivalent paths.

settings.json

Active provider-safe subagent mirror and package settings. Unrelated values are preserved.

zenpi/subagent-provider-profiles.json

Exact provider/model IDs, thinking levels, timestamps, and schema metadata. Retained on uninstall.

zenpi/subagent-provider-leases.json

Ephemeral tokens, process IDs, providers, and timestamps used to prevent cross-process races.

zenpi/

Private wishlist evidence, retirement journals, loop-health source data, checksummed archives, browser artifacts, and bounded managed state.

No profile contains credentials, authentication data, prompts, sessions, history, or a complete settings snapshot. Stop Pi before manually removing retained state.

10

Security

Trust is explicit.

Local

Evidence stays here

Wishlist reports and journals are bounded, sanitized, archive-safe, and never uploaded by ZenPi.

Human

Choice grants authority

Qualification recommends work; one explicit selection starts it.

Exact

Providers do not blur

Different-provider child execution is blocked, even for similarly named models.

Guarded

Critical calls stop first

Known catastrophic model commands and parser uncertainty are blocked before execution.

Pi extensions run with your user permissions. Trusted project settings and dynamically constructed workflow code remain user-controlled boundaries rather than claims ZenPi can sandbox.

11

Development

Contribute with evidence.

Inspect repository guidance before editing, keep changes surgical, and use project-native dependencies. The standard check validates syntax, runs the complete Node test suite, and executes every registry-linked capability validator with isolated prerequisites.

repository check
npm run check
  • Run the narrowest relevant checks while iterating, then the full repository check.
  • Use a temporary PI_CODING_AGENT_DIR for installer integration tests.
  • Inspect the final diff and verify rendered site work at relevant viewports.
  • Do not commit, publish, deploy, or alter remotes without explicit approval.
