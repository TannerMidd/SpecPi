Evaluations

Only the harness
changes.

Six coding harnesses, the same tasks, the same model and the same frozen price list. Anything that differs between the rows is the harness, because nothing else was allowed to move. This is an early suite, and it measures cost and behaviour far better than it measures skill.

Unlike the research page, which reads other people's published studies, these are measurements taken in this repository against this base. The runner, the tasks and the price list are in evals/, and every figure below is redrawn from harness-eval.json by one command.

Summary

01

The suite was built to find out which harness solves more. For a long time it could not answer that, because nearly everything passed. Three rounds of harder tasks changed nothing. What finally produced a difference was adding more harnesses rather than harder work, and the more useful question turned out to be what each harness costs you before the model does anything.

How it is measured

02

Each attempt runs one harness against one task in a disposable home directory, with a fresh copy of the task's workspace and the model pointed at a logging proxy. The proxy records every request and response, so token counts and tool calls are observed rather than self-reported. A task checker then grades the resulting workspace.

  • One model throughout. Every harness runs the same model, so a difference in the table is a difference in how the harness uses it.
  • One price list, frozen. Costs are recomputed from recorded usage against a dated price file, so a provider's pricing change cannot silently rewrite an old result.
  • Graded, not pass or fail. Each task returns a score from 0 to 1, because a boolean verdict throws away the difference between a near miss and no attempt.
  • Scope is checked separately. Every workspace is content-hashed before and after. A harness that edits files the task did not put in scope is recorded as out of scope whether or not it passed.

Attempts that never started are excluded. Harnesses run side by side, and that contention can occasionally stop one launching before it makes a single model call. Such an attempt never ran the task, so counting it as a loss would blame a harness for the evaluation's own plumbing. They are dropped from every average and counted separately as launchFailures in the data file, so the exclusion is visible rather than quietly applied.

Did it solve the task?

03

This is the figure the suite was built to produce, and for most of its life it was the least informative one in the set. Every harness passed almost everything. It is published partly because that flatness is itself a result, and partly because it has finally started to move.

Three rounds of harder tasks were written to try to force a difference. The puzzles seemed demanding: a wire format inferred from fixtures, an interlocking cache policy, a log far larger than the context window. Every harness solved them on the first or second turn, because a capable model solves that kind of problem and the scaffolding around it barely participates. Harder puzzles were never the answer.

What did produce separation was adding harnesses. One of the six now fails a meaningful share of even the smallest tasks, and it does so consistently across tiers rather than in one unlucky run. That is a fact about that harness on this model, not a ranking of the others, which remain bunched near the top where the metric cannot tell them apart.

Read a failure as an observation, not a score. With a handful of attempts per task, one loss and a genuine weakness look identical. The number of attempts behind every figure is in the data file, and where a harness fails it is worth reading that attempt rather than the rate.

What a harness costs before it starts

04

Every model call carries the harness's tool definitions and system instructions. That payload is fixed, it is sent again on each request, and it is the clearest difference between the rows.

The gap is almost entirely tool schema, not prose. A harness that ships twenty-five tools pays for twenty-five tool descriptions on every request, whether or not the task could use any of them. That cost is multiplied by the number of turns and reduced, but not removed, by prompt caching.

Where the overhead actually lands

05

The obvious guess is that a fixed cost per call is a large share of a small task and a rounding error on a large one. That is not what the per-tier spend shows. A longer task means more calls, and the overhead rides every one of them, so the premium travels with the work rather than being diluted by it.

Every figure is relative to the cheapest harness in that tier. Read across a row and most stay roughly where they started: a harness costing twice the lightest on smoke tasks still costs about twice as much on the long one. The ratios move by a little, not by an order of magnitude, and nothing converges.

Two rows do move sharply, and both get more expensive rather than less. That is worth reading as a property of the long task, where a harness that takes more turns pays its per-call overhead more times, rather than as a fixed trait of those harnesses.

This is the number to carry away. A lighter harness is cheaper on small work and stays cheaper on large work. The saving does not evaporate once the task gets serious, which is the opposite of what an earlier version of this page concluded from a smaller set of harnesses and shorter tasks.

The tool surface

06

The proxy counts tool definitions sent and tool calls actually made. They differ by a lot, in every harness.

Every harness here offers far more than it uses, which is expected. A tool has to be offered before the model can decide it is not needed. What matters is the ratio, because the unused definitions are paid for on every call. This measurement is the reason the accounting was rewritten mid-run: an earlier version of the proxy counted offers and labelled them calls, which made the busiest harness look like the most productive one.

What this does not establish

07

This is a starting point. It is a small suite, on one model, on one machine, and it should be read as such.

  • Nothing about capability. Solve rate saturated. No row here supports a claim that one harness does better work than another.
  • One model. Every result is conditional on it. A model that uses tools differently would move the tool-surface figures and could reorder the cost table.
  • Two attempts per cell. Enough to notice flakiness, not enough to put an interval around a solve rate. Where a harness failed, treat it as an observation and not a rate.
  • Synthetic tasks. They are self-contained and deterministic by design, which is what makes them gradable and also what keeps them from resembling real work on a real repository.
  • Defaults only. Each harness runs as installed. A harness with a large tool surface may well be configurable down, and that would change its fixed cost.

The suite will grow. Harder puzzles mostly measure the model, so the promising direction is tasks where the scaffolding has to participate: long sessions where context management decides the outcome, and situations where tools fail and the harness has to recover.
