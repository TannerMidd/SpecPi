Evaluations

Same answers.
Different bills.

Four coding harnesses on Terminal-Bench 2.0, one model, one frozen price list. Nothing separates them on whether the task gets solved. What it costs to get there differs by more than two to one among the rows that could be measured.

This run is still in progress, and the page is published as it stands rather than when it is finished. Every figure is redrawn from terminal-bench-2.json by one command, so nothing here is typed in by hand. Section 07 lists what is missing and what is known to be wrong.

Summary

01

These runs are in progress. Nothing on this page is a final figure. The benchmark was stopped part way and this is what had completed when it was. Arms are missing, one harness's spend columns are placeholders rather than measurements, and one slice is not the same shape as the others. Every number here can still move. Section 07 is the list.

This page used to carry a suite written in this repository, six tiers of it. It was retired because of what it kept reporting: nearly every harness passed nearly every task, so the thing it was built to measure was the thing it could not see. A suite cannot mark its own homework, and after three rounds of harder tasks the honest move was to stop grading and go and find tasks nobody here had chosen.

Terminal-Bench 2.0 is those tasks. The runs below put Pi with no harness at all beside SpecPi + Jev, Oh My Pi and Claude Code, on the same model through the same endpoint, and the first thing they establish is that the outside benchmark does not separate them either.

The shape of the result is the same one the retired suite found and could not defend: harness overhead is charged on every model call, so it scales with the length of the work rather than amortising over it. What is new is that the tasks are somebody else's.

How it is measured

02

Every arm runs the same tasks through Harbor on Docker, against deepseek-v4.1-flash on one endpoint and one key. Nothing about the model, the provider or the task set differs between rows, so what differs is the harness.

Two slices ran. The first was calibration and is reported as such: seven tasks at five attempts, of which six went the same way for every arm. A task that every harness solves, or that none does, carries no information about harnesses, so the second slice widened to thirteen tasks picked for spread rather than for difficulty. The comparison rests on the widened slice; the calibration slice is here because leaving out the run that shaped the design would misrepresent how the design was arrived at.

Reward and token counts are read from Harbor's own per-trial record rather than from each harness's trajectory, because Harbor reports them in one shape for every agent and reward and tokens are the whole of what this section claims. Cost is recomputed from those tokens at the frozen price list, never taken from a harness's self-report: Claude Code prices its own run at Anthropic's rates for a model that was DeepSeek, which overstates by about two orders of magnitude.

The runs themselves are deliberately not in this repository. Terminal-Bench task content carries canary strings that are not meant to enter a training corpus, so only aggregates and public task names cross into the data file.

One task is dropped and one trial is unscored. Every arm's trials on pytorch-model-recovery produce zero tokens in about two seconds, which is the task's environment failing to build rather than four harnesses failing to solve it; counting those cells would put unmeasured work in the denominator. One Claude Code trial ended in a setup timeout and is reported as unscored rather than as a loss.

Did it solve the task?

03

This is the column the benchmark exists for, and it is the one that answers least. The harnesses finish within a few points of each other on both slices, and the gaps that do appear are inside what a few dozen attempts can tell apart.

No pair of rows separates. Pi against SpecPi + Jev is Fisher p = 0.83 pooled, and exactly 30/39 each on the widened slice. Pi against Claude Code is p = 0.55. Reporting any of these orderings as a ranking would be reading noise.

That is worth stating plainly because it is the second suite to find it. The retired tier suite could not separate harnesses on solve rate, and the usual explanation was that its tasks were too easy. These tasks are not this repository's, were not chosen to be passed, and about a fifth of the attempts fail — and the arms still land together.

What it spent to get there

04

With the answers held level, the interesting variable is what each harness burned reaching them. Here the rows are not close.

SpecPi + Jev does the same work on fewer prompt tokens than bare Pi. Same model, same tasks, same solve rate, a quarter less context. The layer's cost is a longer system prompt and an advisor call; what it buys back is fewer turns spent rediscovering the state of the workspace, and on this evidence the trade clears.

Cost follows tokens, discounted by whatever the provider cached. Among the three rows where that discount could be measured, the spread is — and the cheapest row is not the one that solves least.

Cache

05

Prompt caching is what makes a long agent session affordable, so the cached share is the single number that most changes what a harness costs. All three measurable rows sit above 93%, which says the endpoint caches well for every one of them and that the token differences above are real work rather than cache misses.

Claude Code's missing bar is this run's own bug, not a result. Claude Code speaks the Anthropic Messages API and the provider speaks chat completions, so its traffic crosses a translation in this repository. That translation reported prompt tokens but never mapped the provider's cached share onto cache_read_input_tokens, so every trial recorded zero.

Publishing that zero would have said Claude Code destroys cache efficiency, which the run does not show: Pi and SpecPi see 94% on the same endpoint in the same sitting. The value is published as absent, and its cost is published as an upper bound. The mapping is fixed now; the row will be replaced when the re-run finishes.

The sharpest single case is sanitize-git-repo. Bare Pi solved it 0 times in 3, spending about 2.05M prompt tokens an attempt. SpecPi + Jev solved it 3 times in 3 on about 673k. The opposite case is pytorch-model-cli, where every arm mostly failed and SpecPi + Jev failed outright. Both are in the table for the same reason: a page that prints only its best cell is not reporting a measurement.

What this does not establish

07

It is unfinished. The runs were stopped part way, and this page is what had completed when they were. Terminal-Bench 2.0's hard split and a SWE-Gym slice are planned and have not run.

Plain SpecPi is missing. The arms are Pi, SpecPi + Jev, Oh My Pi and Claude Code. SpecPi without the Jev layer did not run, so nothing here separates what the harness does from what the advisory layer does.

Claude Code's cache and cost are not measurements. Section 05 says why. Its solve rate is unaffected — the fault was in what the proxy reported, not in what the harness received — but its two spend columns should be read as placeholders.

Oh My Pi's widened slice is not the same shape as the others. Two launches of the same script raced and wrote into one output directory, so that slice holds six attempts per task rather than three. The trials are independent and all of them count, but they ran at twelve-way concurrency instead of six, and its timeouts may owe something to that.

One model, one provider, one machine. Every figure is deepseek-v4.1-flash through one endpoint on one Windows host. Token counts and cache behaviour are properties of that combination as much as of the harnesses, and a different model would redraw the spend charts.

Nothing here is significant. At a few dozen attempts per arm, the solve-rate column is consistent with the four harnesses being equally capable, and that is how it should be read. The spend columns separate cleanly, and they are what the page is for.
