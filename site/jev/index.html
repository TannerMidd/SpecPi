The Jev layer

A classifier that
returns numbers.

Most harness decisions are small and repetitive: is this tool output still worth carrying, are these two complaints the same complaint, which of these sources matters most. Asking a chat model costs a round trip and returns prose you then have to parse. The Jev layer asks a typed classifier instead and gets a calibrated probability back, then decides in code.

The whole layer ships off. With the master switch off there is no network call, no key read, no consent read and no prompt change: the harness behaves exactly as it did before the layer existed. Everything below describes what happens once someone turns it on.

What it is

01

Jev is a System One model from TypeSafe. It does not write text. You hand it a state object and a set of questions, and it returns a typed answer for each one, evaluated in parallel against that single state. Three answer shapes exist:

  • Choice — pick one of up to 255 options. Returns the choice, a probability for every option, and a confidence.
  • Score — rate against two to ten ordered levels. Returns a possibly fractional score, per-level probabilities, and a confidence.
  • Noul — yes or no, as a bare probability between 0 and 1. It carries no confidence field, which matters: a gate that waited for a Noul's confidence would be gating on a number the model never reported.

Output is free and input is $0.042 per million tokens, so the cost of a decision is the cost of describing the state, not the cost of the answer. That is why questions are batched: several questions against one state cost the same as one.

Where it sits

02

The layer has two halves that share a key and nothing else. The advisor is first-party SpecPi code that answers questions about session state and never holds authority: it cannot call a tool, grant a capability or allow an action. The guard is a separate pinned package that scores commands before the permission system sees them.

Six gates before anything leaves

03

A call reaches the network only after passing every gate below, in order. Any gate that says no ends the attempt silently and the harness runs the path it would have run anyway. That is the whole failure model: no advice is always a valid outcome, so a timeout, a missing key, a refused consent or an unconfident answer all look the same from the outside.

Consent is deliberately separate from the switch. A config flag records an intention; it does not record that a human was told what the intention costs. The first time any system would put state on the wire, a dialog names the destination host, the shape of the data and the byte ceiling. Without an interactive human nothing is sent, ever, so an unattended run cannot be the thing that starts transmitting. The grant is bound to the host it was given for, so pointing the client somewhere else asks again rather than carrying an old answer to a new destination.

Seven systems

04

One design rule governs all of them: ask local state first, and spend a Jev call only on a question local state genuinely cannot answer. Applying it is what removed the largest measured waste from this list. Six of SpecPi's ten tools were offered on every request and called zero times; two of those are only usable once a human has selected an improvement, which is already a fact on disk. They are now withdrawn until one exists, which needs no model and cannot be wrong.

  • Retention decides whether a large read-only tool result is still worth carrying, before it is appended. Jev decides whether; code does the shortening, so the replacement is a deterministic head-and-tail digest and no model-written prose ever enters the transcript.
  • Compaction adds guidance at the one boundary where the prompt cache is discarded anyway, so the advice costs no cache invalidation it did not already incur.
  • Gap clusters capability-gap reports that describe the same friction and scores their impact independently of what the report claimed. This fixes two real defects: semantically identical reports never reached the repeat threshold because their keys differed, and the ranking trusted the reporter's own impact estimate.
  • Sources orders the sources a delegation batch will freeze. It only ever reorders; it never drops one. It also reads two answers the same call already computed and nothing used, and warns before up to 200 files and 8 MiB are frozen for a child that does not look able to answer the question.
  • Progress is the only system aimed at turns rather than input tokens, which is where the money is on the hard tiers: output is 59% of spend at tier 3 and 66% at tier 4. It watches for a session that has stopped moving — a repeated tool call, a run of errors, several turns with nothing written — and only then asks whether it is stuck. It ships set to tell the person rather than the model, because a wrong nudge costs a turn, which is the exact thing it exists to save.
  • Untrusted content prepends a fixed warning line to a fetched page that confidently reads as instructions addressed to an agent. It applies only to web and browser results, never to the agent's own shell output, and it never blocks. It costs no extra call while retention is on, because the same digest answers both questions in one request.
  • Capability arming reads the request once, before anything is sent to the model, and offers a withdrawn tool group when it is confident the task will need one. It activates nothing: it moves a confirmation the person would have seen at turn six to turn zero, which section 06 measures as roughly three times cheaper.

Why the decision happens on arrival

05

The obvious design is to let results accumulate, then rewrite a batch of them. Simulated over the recorded token series that is worth about −12% of long-attempt cost. Deciding on each result before it is appended is worth about −61%. Same classifier, five times the return, for one reason: a rewrite invalidates the cached prefix, and across these runs roughly 94% of prompt tokens are cache reads.

Pricing the rule that shaped everything

06

Every design decision above rests on one claim: changing the tool set partway through a session throws away the provider's cached prompt prefix, and since about 94% of prompt tokens are cache reads priced at a fiftieth of fresh input, that swings the bulk of spend. It is why there is no tool router, why capability arming happens before the first request or not at all, and why advice is never applied retroactively.

It had never been measured here. Believed, reasoned about, consistent with Pi's own documentation — and never once put on a scale. So it was, on three arms of t3-cascade-ledger differing in exactly one thing: when Browser QA's fourteen tools reach the request. Never, at turn six, or from the first request. The decision rule was written down before the run: a collapse in cached tokens with a re-warm costing more than 10% of attempt cost confirms the rule; no collapse drops it.

Arm Tool schema Fresh tokens Cache hit Model cost
Never armed 6,966 27,652 93.1% $0.01212
Armed from turn 1 15,214 28,227 94.2% $0.01411
Armed at turn 6 6,966 52,420 89.5% $0.01777

The rule holds, and by more than the threshold it was given. In three attempts out of three, the request after the flip saw cached tokens collapse to 3,200 — from 25,984, 17,792 and 21,120 — while the prompt kept climbing. One request went from 3,673 fresh tokens to 31,337: the whole conversation so far, re-read at fresh-input prices. The re-warm cost 14.6%, 21.6% and 23.9% of the attempt, 20% on average against a 10% threshold fixed in advance.

The more useful number is the comparison. Arming the same group from the first request cost 16% more than never arming it; flipping it on mid-session cost 47%. Paying up front is about three times cheaper than paying when the need appears. That is what capability arming is for, and it is the whole of what it does.

Two honest limits. Three attempts per arm is enough to see an effect this size and not enough to rank the arms finely; the turn-1 arm also took more turns than the control (18.7 against 16.3), and some of its extra cost is that rather than schema weight. And the plan for this experiment asserted that activating Browser QA rebuilds the system prompt as well as the tool schema, giving a second invalidation path. That is no longer true: the pinned 0.3.0 release moved its guidance into tool descriptions, and the measurement confirms it — system prompt length is identical between the control and armed arms. The claim has been removed rather than left standing. Web access, a third-party package, does still carry prompt metadata.

Calibrating the gate, and what it found

07

The gate turns a probability into a decision, and until now every number in it was a placeholder with a comment saying so. The layer shipped ahead of its own gate. Calibrating it meant asking two different questions, because a threshold can fail in two different ways.

Does the confidence field separate right from wrong? Measured against labels this repository already owns — predicting an attempt's outcome, its task category and its tier from behaviour alone, with the labels withheld. For a Score the answer is yes, and weakly: about two thirds exactly right and 96% within one level, on a fifth of answers, against a 43% majority class. For a Noul and a Choice, on that corpus, the answer is no: both scored at their base rate. No system's pre-registered precision target was met anywhere on any of those curves, and the artifact records that rather than a number chosen to fill the gap.

Can the gate ever fire? This is the question that found a real defect. The retention gate demanded a Score confidence of 0.80 and a value within 0.15 of a level. On a deliberately obvious case — a directory listing of vendor icons during a changelog edit — Jev answered “spent” every time, at confidence 0.73 to 0.85, mostly under 0.80, with the value drifting past the boundary too. So retention could gate through to keep this result and essentially never to this result is spent. The one branch that does anything was unreachable, and no amount of running the layer would have revealed it, because a system that never fires looks exactly like a system whose advice was always to do nothing.

The same check caught a second one in compaction, and a third in code written for this very release: the capability system's first threshold was set above what the model emits even on an unambiguous yes. The fix in each case was to read the operating point off the recorded evidence rather than to pick a number that felt conservative. Thresholds are now pinned by a test to evals/runs/jev-calibration.json, along with the figures quoted on this page, so moving one takes new evidence rather than a new opinion.

On the production questions, where the state carries the material being judged rather than a row of counters, the separation is wide: a planted credential scores 0.96 against 0.04 for a clean report, a page carrying an injected instruction 0.97 against 0.04, a thrashing session 0.89 against 0.30 for one working steadily. That is the gap the gates now sit in.

The guard is a different trade

08

The advisor is fail-silent and holds no authority. The guard is the opposite on both counts, and that is worth stating plainly rather than configuring away. specpi-jev-guard is fail-closed by design: with no key, an unreachable endpoint, or a middle-band verdict in a session with no interactive UI, it blocks the call and says so. There is no setting that hands the decision back to the permission system.

  • Off, which is the default, means the guard is not in the tool path at all and @gotgenes/pi-permission-system decides every call exactly as it did before the package existed.
  • On means the guard decides first, asks a human in the middle band when there is a UI, and blocks when it cannot reach Jev. An outage stops gated work until it is switched off.

The package's own default is enabled: true, so SpecPi writes an inert configuration at install time rather than at first session start — otherwise a fresh install with no key would begin by refusing to run commands.

What it has actually measured

09

Across 259 attempts spanning five tiers, SpecPi with the layer on made 36 Jev calls with zero failures, costing $0.001 in total — about 0.6% of its own model spend. Against the identical base with the layer off:

Read that honestly: the layer has not yet paid for itself. It costs about 9% more per attempt and scores fractionally lower, which at this sample size is noise rather than a result. The two figures moving the right way are the ones its mechanism actually targets — context grows 6% more slowly per turn and fewer tool calls come back as errors — but a shorter session reads fewer bytes regardless of whether anything was elided, so neither is attributable yet.

The missing measurement was the mechanism's own: nothing recorded how many bytes retention actually dropped, so its effect could only be inferred from a cost delta it may not have caused. The ledger now records, per call, whether the advice was taken and what it saved, and the eval runner folds that out of each attempt's disposable home into its report.

Which means the table above is now known to be measuring less than it looks like it is. It was taken before the gate was calibrated — when retention's shortening branch could not fire at all, for the reason section 07 describes. So the row is a comparison between plain SpecPi and plain SpecPi carrying the cost of asking questions whose most expensive answer was unreachable. It is left standing because it is what was actually recorded, and replacing it with a claim would be worse than publishing a number that has since been explained.

With the instrumentation in place, five live runs say something sharper, and it is not flattering. Retention asks three or four times per attempt and has never once shortened anything. Every decline was the same: Jev answered, and reported a confidence below the calibrated bar. On the contrived case it is confident — a listing of vendor icons during a changelog edit scores 0.75 to 0.85 — but on the real reads of a repair chain, where each result feeds the next step, it is genuinely unsure whether the output is spent, and says so.

The threshold is not going to be lowered to fix that. This system's whole asymmetry is that carrying a result costs tokens and dropping the wrong one costs the task, so firing on a confidence the model did not have is the one thing it must not do. The useful outcome is that the claim is now falsifiable: the flagship system does not pay off on this workload, that is visible in a report rather than inferred from a cost delta, and whether it pays off on a session with genuinely disposable output remains untested.

Turning it on

10

Nothing here is on after an install. Each switch has a session form and a startup form, and a session toggle never writes the startup preference.

  • /jev — show the layer's state and change it.
  • /jev on, /jev startup on — the master switch.
  • /jev guard on, /jev guard startup on — the command guard.
  • /jev status — which posture is in force, and whether a key is present.
  • /jev ledger — read back a local hash of every payload ever sent. Every call is recorded in transmissions.jsonl on this machine.
  • /jev forget — revoke consent.

In SpecPi Chat the same switches appear as toggles under package settings, writing the same file the extension reads. One key serves the whole layer: OPENROUTER_API_KEY, since Jev is published on OpenRouter and both halves reach it that way by default. JEV_BACKEND=typesafe selects TypeSafe's direct API instead, which needs a TYPESAFE_API_KEY; the two keys are not interchangeable and the wrong one returns a bare 401.

Retention, processing and logging of what is sent are governed by OpenRouter and TypeSafe, not by SpecPi. That is the reason the layer ships off, asks before its first transmission, caps what a payload may contain, and keeps a local record of every one.
